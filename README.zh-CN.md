# Adaptive Workflow

**让开发方法有依据，让关键判断看得见，让交付结果经得起验证。**

[English](README.md) · [核心规则](skills/adaptive-workflow/SKILL.md) · [评估说明](docs/evaluation.md) · [参与贡献](CONTRIBUTING.md)

Adaptive Workflow 是面向 Codex 的独立开发 Skill。它要求先查看相关代码、问题现象和已有检查，再决定如何推进工作：问题已经清楚时直接处理；仍有关键未知项时，采用能解决该问题的方法；执行过程中出现新证据或需求变化时，及时调整，并保留已有成果。

它提供核心规则和按需读取的方法指引，使用宿主已经提供的工具。安装和使用不依赖其他 Skill、框架或服务。此外，还提供可选工具，用于检查文件状态、检索候选能力，以及按固定提交收集来源材料。

项目当前集中打磨已有能力，优先解决正确性、可靠性、兼容性和使用体验问题，暂停功能扩张和与默认 Codex 的对照实验。此前的实验未证明它稳定优于默认 Codex，也未证明普遍的 Token 节省；相关结果与限制保留在[历史报告](docs/discovery-validation-2026-10-15.zh-CN.md)中。当前检查方式见[工程验证说明](docs/evaluation.md)。

## 核心能力

- **让调查有具体抓手。** 比较不同解释，选择能够区分假设的检查；针对身份混淆、异步执行顺序、失败恢复等边界收集证据。
- **按实际需要安排工作。** 简单修改直接完成；根因不明、验证不足、接口需要协调或改动影响较大时，再增加必要的调查、规划、测试或审查。
- **在对话中说明判断。** 把发现的问题、选用的方法、下一步行动和验证目标联系起来，让用户能理解工作为什么这样推进。
- **接续长任务，保留有效成果。** 将结论与它依赖的代码、需求和环境对应起来；发生变化时，重新检查受影响的部分，继续使用仍有效的成果。
- **发现并选择合适的能力。** 先检查已有能力；不足时查找尚未安装的候选，核查准确来源、实际指令、运行前提和后续成本，再决定采用、借鉴或继续直接处理。
- **交付有验证依据的结果。** 说明改了什么、检查证明了什么、还有哪些限制；达到验收要求后结束工作。

这些能力通过指引 Codex 的判断和行动发挥作用。Skill 本身不独立运行任务，也不绕过宿主的工具权限和执行控制。

## 适用场景

当有限探索后仍无法确认根因、现有测试没有覆盖关键行为、需求差异会改变方案，或者存在实际的协作与审查需要时，可以使用本 Skill。执行中的发现推翻原判断，也属于它需要处理的情况。

对于边界明确、容易验证的小修改，直接修改并检查即可。任务看起来复杂、涉及多个文件，或者恰好装有其他能力，都不足以单独成为增加流程的理由。

## 安装

在 Codex 中发送以下安装请求：

```text
Install the standalone skill from https://github.com/sky-k111/adaptive-skill-router/tree/main/skills/adaptive-workflow.
```

也可以把仓库中的整个 `skills/adaptive-workflow` 文件夹复制到支持的 Skill 目录，例如 `~/.agents/skills/adaptive-workflow`。请保留目录结构，不要只复制正文。安装后若列表没有显示，可重启 Codex。目录与发现规则见 [OpenAI 官方文档](https://learn.chatgpt.com/docs/build-skills)。

遵循独立 Skill 的工作指引无需安装 Node.js。可选辅助脚本和仓库命令行工具需要 Node.js 22 或更新版本；也可以使用宿主已有的文件和浏览工具完成相应工作。

## 使用

在开发请求中指定本 Skill 即可，例如：

```text
Use $adaptive-workflow to investigate this failure, make the necessary change, and verify the requested behavior.
```

实际任务可以继续用中文描述。安装后，Codex 也可以根据任务与 Skill 描述的匹配情况考虑使用；安装并不意味着每条消息都会触发它。用户要求和项目约束始终决定工作边界。

### 用真实任务体验

从项目里一个能够复现的问题开始，说明现在的现象、期望结果，以及已有的复现步骤或测试。下面的占位内容可以替换成中文：

```text
Use $adaptive-workflow to fix this issue in the current project: [observed behavior]. Expected: [required behavior]. Reproduce with: [command or test].
```

把过程说明与实际改动对照着看：依据是什么，为什么这样处理，检查证明了哪些行为。原因明确的小问题可以直接修正。实际采用本 Skill 时，首次说明实质判断的消息应提到 Adaptive Workflow，并说明它帮助作出了什么决定。

执行中需要调整需求时，把新增的预期行为说清楚。随后应能看到哪项判断发生变化、哪些已完成的工作继续有效。这种体验可以帮助你观察它如何适应变化，但不能单凭一次体验判断它优于默认 Codex。

### 为项目寻找缺少的能力

可以直接描述需要补齐的能力，例如：

```text
用 $adaptive-workflow 为当前项目寻找适合的浏览器交互测试 Skill。先检查已有能力，再核查候选来源、实际指令和运行前提，说明选择依据后采用。
```

宿主先检查当前已有的 Skill；不足时，可以通过已有浏览工具或随包附带的脚本查找外部候选：

```sh
node <skill-directory>/scripts/search-skills.mjs --query "browser interaction testing" --limit 5
```

这个可选脚本只向 skills.sh 发送明确填写的检索词，以及可选的作者和结果数量，不读取项目文件，也不会安装软件或执行搜索结果。请使用不含敏感信息的能力关键词。当前支持 GitHub 仓库来源，结果包含准确来源和链接；宿主仍需检查候选正文、所需工具及兼容性，安装量不代表质量。网络失败、接口格式变化和成功但无结果会分别处理。选择与安装边界见[能力选择指引](skills/adaptive-workflow/references/capability-selection.md)。

检索会按关键词覆盖情况重新排序，同时保留服务方的原始排名。已知需要或排除的能力可以通过 `--require`、`--exclude` 明确指定，远程结果会说明过滤原因；这些仍是文字匹配信号，不能代替对实际用途的判断。

需要核查来源时，可用随包提供的 `collect-source.mjs`，把正文、调用元数据、许可证和有限范围内的支持文件固定到同一提交。材料缺失会逐项报告，“收集完成”不会被当作“审查通过”。详见[来源材料收集说明](docs/source-review.md)。

仓库命令行工具还提供 `discover "关键词"` 和附带联网检索的 `discover "关键词" --online`，详见[可选工具说明](docs/router.md)。不需要额外安装某个发现类 Skill 或包管理器。脚本使用的是检索服务自身命令行工具采用的外部接口，其持续可用性仍取决于服务方。

本地候选会附带校验标识。使用 `inspect --expect` 读取时，工具会核对入口正文、调用元数据和实际路径，发现变化便停止，避免沿用已经过期的选择。具体范围见[版本校验说明](docs/router.md#reading-the-version-that-was-selected)。

如果当前网络需要代理，可以在 Node.js 24.14 或更新版本下通过 `--proxy URL` 或 `ASR_HTTPS_PROXY` 使用已有的可信代理；仓库工具也支持私有的项目配置。代理地址不随项目发布，证书校验保持开启。具体配置和旧版运行时的替代方式见[代理支持说明](docs/router.md#existing-proxy-support)。

## 在对话中如何体现

工作推进到重要判断或实质进展时，应让用户知道：目前确认了什么，还缺什么信息，为什么采取这个方法，接下来要检查哪种行为。需求或证据变化时，应说明原方案哪里需要调整、哪些成果可以继续使用。交付时，应明确验证范围和未验证事项。

例如，调查缓存问题时，可以这样说明：

> 现有测试只检查了同一账户的重复读取，但缓存键没有区分账户。我会补充不同账户的返回结果和读取次数检查，再修正相应的数据边界。

这类说明必须对应真实发现，不能成为固定台词。简单任务可以简短交付，不要求重复播报启用状态、逐个解释工具调用，或额外生成展示过程的报告。

## 执行规范

### 按需要读取方法

核心规则关联三份方法指引，各自在遇到相应问题时使用：

- [问题调查](skills/adaptive-workflow/references/investigation.md)：当原因仍不确定时，选择能区分不同解释的检查；对异步问题，用可控的执行顺序验证关键边界。
- [能力选择](skills/adaptive-workflow/references/capability-selection.md)：判断候选能力能带来什么、需要哪些前提、会增加多少后续工作，并说明实际采用的部分。
- [任务续接](skills/adaptive-workflow/references/continuity.md)：任务恢复、交接或需求变化时，判断哪些旧结论需要重新验证，哪些工作可以保留。

这三份指引不是必须依次完成的阶段。明确的小修改无需读取全部参考，也无需建立交接记录。

需要为交接保留文件证据时，可以使用续接指引中的可选工具：

```sh
node <skill-directory>/scripts/check-evidence.mjs capture --root <project> --output <project>/local-evidence.json <relative-file> ...
node <skill-directory>/scripts/check-evidence.mjs check --root <project> --record <project>/local-evidence.json
```

它只记录明确选定的文件，之后报告文件是否变化或缺失；已有记录不会被覆盖，项目范围外的路径会被拒绝。文件未变化不等于测试已通过，也不能证明所有相关依赖都已记录或环境没有变化。记录包含本地项目路径，应留在本地。退出状态和具体限制见任务续接指引。

### 工作边界

核心规则明确要求：新增流程必须有具体依据，验证要覆盖实际风险，过程和结果必须如实说明。不能编造发现、虚报调用，也不能为了套用某种方法扩大任务范围。

可选资源不是必需依赖。采用前必须阅读相关指引并检查运行前提；只借鉴部分方法时，应说明实际采用的部分。不能把“发现了某项能力”当成“已经调用”，也不能把测试通过扩大为未经检查的质量结论。

选择方法不产生新的操作权限。项目要求的检查和必要的授权边界不能省略。验收完成后应停止追加工作，不能把可选优化变成新的交付义务。

## 验证与支持范围

当前支持 Codex。核心规则和界面说明统一使用英文，但执行时应按用户的语言沟通。中文版说明单独维护，以准确、自然的表达为准。

检查仓库实现及路由策略时，运行：

```sh
npm ci
npm run check
```

这组检查需要 Node.js 22 或更新版本。检查通过只能证明相应测试覆盖的行为，不能据此宣称优于默认 Agent，或节省了 Token。行为评估方法及限制见 [评估说明](docs/evaluation.md)。本地日志、私人配置和生成的接入文件不随源码发布。

[重复行为对照](docs/benchmark-2026-10-11.zh-CN.md)记录了一个限定的收益场景：同一流程技能库下，处理要求明确的小修改时，输入 Token 减少，独立验收结果保持一致。直接与普通 Codex 比较时，没有取得重复优势。报告保留了全部结果及限制，不能据此宣称安装后自动生效或普遍节省 Token。

[真实项目归档修复](docs/real-project-2026-10-11.zh-CN.md)中，各组都通过了固定验收，但补充复核仍发现兼容性回归，没有证明稳定的质量或成本优势。报告保留了副本准备过程的缺陷、全部结果及据此进行的具体方法修正。

[冻结版本的新任务对照](docs/heldout-2026-10-11.zh-CN.md)完成了两项新源码问题的 12 次独立会话，三种配置的验收结果相同，没有达到预登记的质量或重复输入减少标准。报告保留全部结果，并说明工作副本准备、共享依赖及缓存控制的实际边界。
