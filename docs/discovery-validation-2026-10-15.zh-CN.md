## 对照如何进行

任务来自本项目原本就存在的两个缺陷，没有人为植入故障：

1. 命令会悄悄接受不适用的参数，例如 `scan --write`、`init --native`。验收要求在读文件、启动原生发现、联网或写入之前拒绝非法组合，同时保持合法命令、帮助和版本输出。
2. 检索工具拒绝超大响应时，没有释放响应体。验收要求先等待清理完成，再报告原来的大小限制错误；清理失败不能覆盖原错误，不能读取正文，也不能触发响应重试。

运行前，两套独立检查都在原实现上失败。任务、提示、Skill、源码副本和验收脚本先冻结，再启动模型。注册时间为 **2026-10-15T03:39:42.389Z**，注册记录的 SHA-256 为 `94639171a3ce388473fd3627e8d23e2fccdda907b172b3263ba2e2c7c07b0aae`。测量的是已包含本轮发现功能、尚未合入这两处修复的开发快照，不能误称为某个旧发布提交的原样版本。

每个任务重复两次，每次分别运行默认组和启用组，共 8 次，固定使用 CLI 0.162.0、gpt-6.1-sol/high、480 秒上限、独立 Git 根目录和独立 CLI 配置目录。默认组没有安装可选工作流 Skill；启用组只增加冻结的 Adaptive Workflow，并明确调用它。两组使用同样的产品源码、公共来源材料、基础能力和中性项目指令。

任务要求判断候选是否值得采用，也允许拒绝全部候选。为了让材料一致，模型运行期间不做外部检索；真实联网收集另行验证。因此这不是完整联网流程的成本对照，也不是当前桌面会话的自动启用测试。

## 交付与结论

每个任务采用首份通过独立验收的启用组修复合入项目；默认组也有通过的修复，这个合入选择不代表哪组质量更高。组合验证结果为 **140 项通过、2 项文件符号链接检查因本地 Windows 权限跳过，路由策略 10/10**。本机安装目录经过修改检查和备份，10 个资源与仓库版本逐项一致。原始模型日志、第三方正文、私人配置和实验副本不进入发布包。

本次题目由作者选择，缺陷已经被作者识别，候选材料也经过筛选；它不是盲测、随机生产样本或未见任务。共享依赖、并行运行和服务端缓存没有完全控制，耗时只能描述这次观察，不能作因果推断。

可以确认的工程价值是：检索结果有更清楚的匹配依据，来源材料可固定版本收集，失败状态可追踪，两处真实缺陷有了回归保护。不能确认的是稳定优于默认 Codex。接下来应围绕这些具体能力积累真实使用证据，而不是继续添加通用工作流承诺。此前的[未见任务负结果](heldout-2026-10-11.zh-CN.md)也继续保留。
