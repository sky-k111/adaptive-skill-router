# 真实项目验证：期刊归档校验

[完整英文记录](real-project-2026-10-11.md)

这次让六个全新 Codex 会话修复 GitHub Trending Digest 离线期刊模块中的真实缺陷。六组都通过了预先固定的外部验收，但后续复核仍发现兼容性回归。**本轮没有证明 Adaptive Workflow 能稳定提高质量或降低成本。**

## 问题来自哪里

使用的是 [GitHub Trending Digest](https://github.com/sky-k111/gh-trending-digest) 当时的本地工作区，其中包含已经存在、尚未提交的期刊模块。仓库基础提交为 `d45d05d835e26626c203959440d8d288e5ec711f`，仅检出这个公开提交不能还原本次任务。实验复制了相关源码、原测试、字体与示例归档，没有往实现中植入错误，也没有复制业务环境配置、私人数据库或线上数据。

实际复现了两个问题：修改归档清单中的 PDF 字节数，文件不变，程序仍然认定归档有效；清单结构错误时，部分输入会泄漏内部异常。原项目已有的 51 项测试全部通过，说明这些检查尚未覆盖相关行为。

执行前固定的外部验收在原实现上得到 24 项失败、22 项通过、1 项因 Windows 文件符号链接权限跳过。单独编写的校准修复通过了全部 46 项可运行检查及原有 51 项测试，用于确认验收要求可以满足。

修复范围包括 JSON 结构与重复字段、冻结内容和清单的一致性、文件名与目录边界、实际大小和哈希，以及非法导入、备份恢复失败时不能留下期刊数据。要求保留历史 schema 1/2/3、截图、幂等性和恢复行为，不新增采集、邮件、调度或界面。

## 怎么比较

三种配置各重复两次：无额外流程 Skill、正常使用现有的 13 个流程 Skill、同一技能库加上明确调用的 Adaptive Workflow。普通技能库组没有被要求强制规划或等待审批。

使用同一模型 `gpt-6.1-sol`、同一 `high` 设置和 Codex CLI `0.162.0`，每组独立配置目录和 Git 根目录，最多运行 12 分钟。六组使用冻结的同一份源码、原断言和样本内容。上下文审计确认没有混入个人自适应全局规则或父项目接入指令；原断言和样本字节均未改变。比较期间没有修改被测 Skill，测量版本来自 `cb7f9731dc28beff8693787c4168ebbeda00d727`。

预先登记的质量标准是：Adaptive 两次都通过，而对照组最多通过一次。成本标准是：双方通过，且 Adaptive 两次的未缓存输入均至少减少 30%。这两个标准都没有达到。

| 轮次 | 无额外流程 Skill：未缓存输入 | 普通技能库：未缓存输入 | Adaptive：未缓存输入 | 固定外部验收 |
| --- | ---: | ---: | ---: | --- |
| 第一次 | 71,512 | 99,848 | 82,404 | 三组均 46 通过、1 跳过 |
| 第二次 | 58,588 | 96,410 | 79,240 | 三组均 46 通过、1 跳过 |

Adaptive 相比普通技能库，观察到的未缓存输入减少约 17.5% 和 17.8%，总输入减少约 45.9% 和 19.7%。相比无额外流程 Skill，未缓存输入增加约 15.2% 和 35.2%，总输入也更多。完整输入、缓存、输出、时间和各组回归结果保留在英文记录中，没有只报告有利指标。

各组都增加了自己的测试，数量不同。测试更多不等于覆盖更好，也不能用它代替独立验收。

## 本轮准备过程的缺陷

副本复制尚未全部结束时，提前运行了基线检查，导致第二轮副本带入生成的 Python 缓存。初始 Git 索引中，无额外 Skill 组有 23 个缓存文件，另外两组各有 24 个；第一轮三组均没有。源码、原断言和样本哈希仍然一致，但缓存状态不同，模型也花了额外工作清理缓存。

因此，第二轮不能作为严格的干净环境成本对照，本轮成本只作观察，不作为 Skill 优势证明。没有删除或替换这些结果。服务端缓存命中也未控制；并发运行的时间不能证明速度提升。部分非必要清理被自动审批拒绝，但没有阻止完成修复。

外部验收的一项真实文件符号链接检查始终因本机权限跳过。某组将自己新增的跳过用例替换为模拟路径解析检查，最终显示没有跳过；这不能解释为真实符号链接已验证。文件边界来自指令，并非操作系统隔离。本轮只有一个真实问题，也不能证明安装后会在当前桌面对话中自动生效。

## 通过测试后，仍然发现了什么

复核发现：可选 Markdown 附件原本允许使用安全的自定义文件名。原实现和校准修复都接受这个合法变体。任务只要求六种必需格式使用对应生成文件名，部分修复却把限制扩大到了可选 Markdown。

这项检查是在第一轮无额外 Skill 组与 Adaptive 组完成后另行登记的，属于事后补充诊断。随后对六组统一检查，没有改动原来的固定验收，也没有把发现反馈给正在执行的模型。

| 轮次 | 无额外流程 Skill | 普通技能库 | Adaptive |
| --- | --- | --- | --- |
| 第一次 | 错误拒绝合法输入 | 保留兼容性 | 错误拒绝合法输入 |
| 第二次 | 错误拒绝合法输入 | 错误拒绝合法输入 | 保留兼容性 |

所以，固定验收全通过仍不能代表所有交付要求都已验证。Adaptive 和普通技能库在这个补充案例上各通过一次，不能宣称稳定的质量优势，更不能把事后检查包装成预先登记的独立留出结果。

## 实际交付与 Skill 修正

已保留第一轮普通技能库组的修复副本和可审阅补丁。选择它是因为固定验收、完整回归和补充兼容性检查均通过。交付副本再次运行完整回归，得到 196 项通过、3 项权限限制跳过。这份修复不是 Adaptive 独有成果。原项目期间仍有其他更新，实验没有覆盖其工作区、向其仓库推送、发送邮件或改变调度。

六组比较结束后，才针对这个实际遗漏更新 Skill：收紧规则时，先明确规则约束哪些字段、模式或调用方，再检查一个容易被过度限制的合法输入。旧程序接受过的输入，也需要依据当前契约判断是否仍然有效。具体方法放在按需读取的调查参考中，仅在兼容性尚未验证时采用，不给普通修改增加固定流程。

更新后，另开一个干净会话复核第一轮 Adaptive 的修复。提示只要求依据原任务进行交付前审查，没有透露怀疑的错误或预期修法。该会话实际读取了新的调查参考，先用探针排除了没有证据支持的 Unicode 假设，随后复现可选附件的兼容性回归。它只改动一行实现，补充 8 个参数化用例，保留原测试文件中的全部 22 个既有函数、原断言和样本字节。

独立验收为 46 项通过、1 项权限跳过，补充兼容性检查通过，完整回归为 175 项通过、3 项权限跳过。这个第七次会话说明具体方法已被采用，并完成了已知案例的修正。该案例参与了方法设计，任务也从首次修复变成了复核，没有同条件的旧版复核对照；因此不能把它当作独立留出的质量优势或节省证明。

原始日志、精确提示、验收脚本、源码哈希、冻结 Skill、缓存审计、补充检查和补丁保留在本地。行为实验副本、私人配置、机器路径和第三方 Skill 副本不会随项目分发。[之前的合成实验](benchmark-2026-10-11.zh-CN.md)及其正、负结果仍然保留，不能用本轮替换，也不能把旧场景中的节省外推到复杂项目。
