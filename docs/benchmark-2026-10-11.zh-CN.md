# 重复对照实验：什么时候 Adaptive Workflow 有实际收益

[完整指标与方法说明（英文）](benchmark-2026-10-11.md) · [评估原则](evaluation.md)

本次找到的优势有明确边界：**装有较多流程 Skill、修改要求已经清楚时，实际使用 Adaptive Workflow 可以减少不必要的流程读取和输入 Token，同时保持验收结果。** 本次没有证明它比未安装额外工作流的 Codex 更擅长解决问题，也没有证明它普遍更快。

## 最有说服力的对照

两组都装有同样的 13 个流程 Skill，使用同一模型和设置，处理同样的任务：修正一个标题，并让路径标签保留调用者传入的完整字符串。一组正常处理，另一组额外安装并明确调用 Adaptive Workflow。普通组没有收到“必须规划”或“调用全部 Skill”的要求。

每组使用独立的新会话重复两次。两轮中，双方都通过了全部三组独立验收，保留了原有测试断言，也没有扩大修改范围。

| 轮次 | 普通技能库：未缓存输入 Token | 使用 Adaptive：未缓存输入 Token | 减少比例 | 双方独立验收 |
| --- | ---: | ---: | ---: | --- |
| 第一次 | 23,426 | 10,281 | 56.1% | 均为 3/3 |
| 第二次 | 18,436 | 11,173 | 39.4% | 均为 3/3 |

包含缓存部分的累计输入 Token 分别减少 35.6% 和 22.9%。执行记录也说明了差异来源：普通组执行了 6 次和 4 次读取 Skill 正文的命令，Adaptive 组两轮均为 2 次。普通组实际读取了多份调试、测试或验证指引；Adaptive 组查看共同的入口指引及自身规则后，检查实现、直接修改并完成验证。

一次读取命令可能包含多个文件，也可能重复读取同一文件，因此这些次数不等于调用了多少个 Skill。减少读取次数本身不是成功标准，保持验收结果才是前提。耗时没有稳定下降，不能据此宣称提速或降低实际账单金额。

## 强行套用完整流程的结果

另有一组明确要求先完整规划，再按执行流程处理同样的任务，用于模拟选错方法后的流程滥用。它在两次小修改和两次交接故障任务中，均生成了计划或规格文档，然后要求人工审阅，源码仍未修改。

Adaptive 组四次均完成了修改与验收，而该组的小修改验收为 0/3，交接故障验收仍为原始代码的 2/10。这说明，在这些任务上硬套带审阅门槛的完整流程，会造成额外等待和未完成交付。

这组是有意设置的滥用对照，不能代表第三方工作流的正常使用。上面的同一技能库对照没有强制这类流程，因此它提供了更直接的输入量收益证据。

Adaptive 组没有同时收到强制规划的要求。这比较的是不同方法选择带来的结果，不能说明本 Skill 应覆盖用户明确指定的流程。

## 没有取得优势的情况

直接与没有额外工作流的 Codex 比较时，两轮小修改和两轮交接故障修复，双方全部通过独立验收。Adaptive 没有达到“每轮正确率更高”或“每轮未缓存输入至少少 30%”的条件。

交接任务涉及已经变化的串行队列实现：失败后继续执行、各任务保留原始结果、无参数调用、drain 的调用时快照，以及 close 返回稳定的 Promise。Adaptive 确实检查了旧文件指纹，但普通 Codex 也正确识别并修复了问题。**多做了证据检查，不等于已经证明独有的正确率收益。**

| 场景与轮次 | 普通 Codex：未缓存输入 Token | Adaptive：未缓存输入 Token | 双方独立验收 |
| --- | ---: | ---: | --- |
| 小修改，第一次 | 7,411 | 13,093 | 均为 3/3 |
| 小修改，第二次 | 9,310 | 7,385 | 均为 3/3 |
| 交接故障，第一次 | 13,229 | 30,154 | 均为 10/10 |
| 交接故障，第二次 | 11,184 | 18,523 | 均为 10/10 |

之前的旧版与新版对照同样没有证明正确率优势，新版还消耗了更多时间和 Token。完整结果保留在评估文档中，不因本次找到一个收益场景而删除。

## 实验边界

共完成 16 个独立会话：两个场景、三种基本配置各重复两次，再补充四个同一技能库的控制会话。基本实验先确定任务、验收、指标和停止条件；补充控制也在执行前登记。全部结果都记录在英文报告中，没有只保留胜出的样本。

所有会话使用 Codex CLI `0.162.0` 和继承的 `gpt-6.1-sol`、`high` 设置，使用独立 CLI 配置目录与 Git 根目录。上下文审计确认没有混入个人的自适应全局规则或父项目接入指令；Skill 正文与冻结副本一致，原测试断言没有被削弱。一个原测试文件仅追加了新测试，其原有内容保持不变。文件边界来自指令和配置控制，并非操作系统隔离。

任务是合成样例，每种比较只有两次重复，不能外推为所有项目和技能库的平均收益。测试明确调用了本 Skill，不能证明“安装后自动生效”。新的 CLI 会话也不等于当前桌面会话。如果全局指令已经有相同的按需选择原则，额外安装本 Skill 的收益可能更小。

原始日志、精确提示、文件哈希、冻结副本、修改记录、独立验收输出和上下文审计均留在本地。它们包含机器路径，不随源码分发；第三方 Skill 副本和私人配置也没有发布。

## 当前应采用的定位

现有证据支持把 Adaptive Workflow 定位为按需选择开发方法的 Skill，主要用于减少过宽触发和流程叠加造成的额外工作。对明确的小修改，保留直接执行和必要验证；对已有明确原因的问题，不为展示作用而增加流程。

后续优化应先缩短通用入口，保留按需读取的具体方法；新增能力应以默认行为中观察到的失败为依据，并在未用于设计的任务上复验。当前不应宣传它能普遍提升模型智力、代码质量或节省 Token。
